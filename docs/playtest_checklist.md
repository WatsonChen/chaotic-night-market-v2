# Playtest Checklist

建立時間：2026-07-17
用途：在 Godot 編輯器裡實機跑一輪，驗證這幾輪重構（角色資料化、控制抽象、音效優先級、
補貨事件、前期節奏緩衝）有沒有把原本的手感弄壞，並收集調參用的第一手感受。**這份文件只
記錄怎麼測、測什麼——測完的結果、要改的數值，回頭寫進對應的 export 參數或另外找 Claude 討論。**

每一項請填「正常 / 有問題 / 備註」三欄之一（或都填）。有問題的項目附上大概的重現方式
（例如「P2 連續 burst 時」），方便之後回頭定位。

---

## 測試前準備

1. 打開 `main.tscn`，選到 `Main` 節點，在 Inspector 找到 `Restock Event`、`Hazard Event`、
   `Run Summary Debug` 三個分組
2. 把 `Restock Debug Key Enabled`、`Hazard Debug Key Enabled`、`Stats Preview Debug Key Enabled`
   都打勾（測完記得關掉或不用存檔，三個開關都不影響正式版）
3. 建議開兩次 Play：第一次用預設 P1/P2（熱狗/珍奶）跑基礎回歸 + 音效 + 兩個事件；
   第二次照下面「角色 Resource 測試」的步驟把 P2 換成雞排攤再跑一次
4. 有雙人測試條件的話盡量找第二個人一起測——這款遊戲的核心是雙人互動（友火、雙人破防、
   事件掩護），單人分飾兩角很難測出真正的手感
5. 遊戲畫面左上角（客訴數字左邊）現在會顯示「P1：XX　P2：XX」——這是這輪新加的，
   之後每次測試先看這行文字，確認角色有沒有指到你以為的那個

### 如果你很快就 Game Over，看不到事件是正常的

補貨事件正式預設**開場 45 秒**才觸發（`restock_trigger_elapsed`），清除障礙事件更晚
（`hazard_trigger_elapsed=64.0` 起算，實際可能因為排程保護再往後延，見下面第六節）。
如果一局撐不到這些時間點（例如撐了 29 秒），本來就不會看到事件，這不是 bug。有兩種
方式可以測到：

- **按 R/F9（補貨）或 H（清除障礙）**（推薦，最可靠）：對應的 Debug Key Enabled 打開後，
  遊戲中隨時按鍵立即觸發，不受正式觸發時間限制，事件結束後還可以再按一次重測。
  R 是備用鍵——Mac 上 F9 常被系統快捷鍵佔用不好按，用 R 就好
- **調低觸發時間**：補貨用 `Restock Trigger Elapsed Debug`（預設 `-1` 不生效），改成例如
  `10` 就會開場 10 秒自動觸發；清除障礙目前沒有對應的 debug 覆蓋參數，只能靠 H 鍵或
  縮短 `Hazard Trigger Elapsed` 本身測——如果你想測「事件自動觸發」這個時機判斷本身
  有沒有問題（而不是手動按鍵觸發的路徑），才需要用這個，一般測手感按鍵就夠

## 零、前期節奏測試（Early Game Grace）——最優先測這個

目的：確認新增的開場緩衝期有沒有解決「補貨事件還沒出現就 Game Over」的問題。**這一節請正常
遊玩，不要開 debug 快捷鍵**——重點是驗證「一般玩家不靠 F9/R 作弊，正常玩能不能活到 45 秒」。

前期節奏目標：**玩家應能穩定撐到 45 秒看到補貨事件觸發，不需要靠任何 debug 手段。**

| # | 測項 | 目前預設值 | 正常 / 有問題 / 備註 |
|---|---|---|---|
| 0.1 | 正常遊玩（不按 R/F9），能不能撐過 45 秒看到補貨事件的開始 banner + 螢幕閃光 | `early_grace_duration=45.0` | |
| 0.2 | 開場前 45 秒的敵人數量，感覺是「有難度但可以應付」還是「還是太多、喘不過氣」 | `early_enemy_multiplier=0.65` | |
| 0.3 | 開場前 45 秒波次之間的間隔，感覺是「剛好夠喘口氣」還是「太久沒事做、無聊」 | `early_wave_interval_multiplier=1.35` | |
| 0.4 | 前 45 秒確認沒有出現大型饕客（有笑臉的大紅圈、頭上兩條破防條的那種） | `early_disable_big_enemy=true` | |
| 0.5 | 45 秒一到，敵人數量/頻率有沒有明顯感覺「變多了」——這代表緩衝期正確結束、回到正式節奏 | | |
| 0.6 | 45 秒前如果客訴已經意外衝到 stage 2（4 次以上），敵人數量是否還是有被壓低（不是完全沒差） | | |

如果 0.1 仍然常常失敗（正常玩還是撐不到 45 秒），代表 `early_enemy_multiplier`/
`early_wave_interval_multiplier` 需要再往下/往上調，或者問題根本不在生成節奏而是別的地方
（例如玩家自己還在熟悉操作、擊退連鎖太容易誤傷自己）——這個要靠你實測回報才能判斷。

## 二、角色 Resource 測試：熱狗、珍奶、雞排

目的：驗證 `PlayerCharacter` Resource 抽象在第三個角色（雞排攤）身上是否成立。

`Character Test Override` 分組，把 `P2 Character Override` 指到
`resources/characters/chicken_cutlet.tres`，重新 Play。左上角的「P1：熱狗攤　P2：雞排攤」
文字會跟著變，可以直接確認有沒有指對。測完把 override 清空（拖回空/None）就會恢復預設珍奶攤，
不用記得改回程式碼。`P1 Character Override` 同理，測 P1 用別的角色也是同一套流程。

| # | 測項 | 參考數值 | 正常 / 有問題 / 備註 |

## 三、音效優先級測試

目的：驗證 LOW/HIGH 雙通道池 + cooldown 保護有沒有真的解決「訊息音被洗掉」的問題。
建議故意製造混亂場面（例如站在一群敵人中間、讓 P2 對著敵群連續開火）來測極端情況。

| # | 測項 | 正常 / 有問題 / 備註 |
|---|---|---|
| 3.1 | `COMPLAINT`（客訴 +1）：即使敵人密集抵達中央、命中音很吵的時候，客訴音還是聽得到、沒被蓋掉 | |
| 3.2 | `BIG_BREAK`（大型饕客破防）：命中瞬間音效夠不夠明顯、有沒有被同時發生的其他命中音吃掉 | |
| 3.3 | `CHAIN_HIT`（擊退連鎖命中）：撞進一群敵人時，這個音效聽起來是「有節奏的連續打擊感」還是「太密集像機關槍」還是「太稀疏漏拍」 | |
| 3.4 | `SPIKE_WARNING`（失控潮/衝刺警告）：警報聲響起時，有沒有讓人下意識想找場上發生什麼事（有沒有達到「警告」該有的效果） | |
| 3.5 | 突變選擇畫面出現（`MUTATION`）跟突變生效瞬間（`MUTATION_APPLY`）兩個音效是否聽得出差異，還是感覺像同一個音效響兩次 | |
| 3.6 | 勝利 / 失敗音效（`WIN` / `LOSE`）是否正常播放、沒有被搶拍或漏播 | |
| 3.7 | 整體音量平衡：新加的三個音效（`CHAIN_HIT`/`MUTATION_APPLY`/`SPIKE_WARNING`）音色會不會跟舊的 7 個太像分不出來，還是明顯違和突兀 | |

## 四、補貨事件測試

目的：收集數值調參的第一手資料。按 R 或 F9 多測幾次（不用等 45 秒），每次都記一下。

**觸發方式**：確認第一步「測試前準備」已把 `restock_debug_key_enabled` 打開，遊戲中按 **R 或
F9**（兩個鍵一樣，Mac 建議用 R）。只要事件目前沒在進行中，可以連續按好幾次重複測試。

| # | 測項 | 目前預設值 | 正常 / 有問題 / 備註 |
|---|---|---|---|
| 4.1 | 補貨區出現的位置，跑過去會不會覺得太遠 | 四邊緣挑距離較近的兩個之一 | |
| 4.2 | 補貨區半徑（56px）夠不夠站，兩人同時擠進去會不會卡住彼此 | `restock_zone_radius=56` | |
| 4.3 | 需要站滿 3 秒，會不會覺得太長（任務感太重）或太短（沒感覺） | `restock_required_time=3` | |
| 4.4 | 14 秒的總時限會不會太寬鬆（幾乎不會失敗）或太緊（常常來不及） | `restock_timeout=14` | |
| 4.5 | 「離開區域不歸零、只暫停」這個預設行為，玩起來是否比較好玩、公平 | `restock_progress_decays_when_empty=false` | |
| 4.6 | 進度 UI（`restock_progress_label`）文字會不會太大/位置擋到重要畫面（客訴數、時間） | 位置在 Y=270 附近 | |
| 4.7 | 補貨成功的回饋（客訴 -2、暫停生成、綠色特效、音效）加起來夠不夠有「鬆一口氣」的感覺 | `restock_success_relief=2`、`restock_success_pause=2` | |
| 4.8 | 補貨失敗的回饋（多生成 2 隻敵人）夠不夠有懲罰感，還是感覺不出差異 | `restock_fail_spawn_count=2` | |
| 4.9 | 補貨事件進行中，敵人照常生成會不會讓事件變得幾乎不可能完成（太難）或完全不受影響（太簡單） | | |
| 4.10 | 事件開始時的提示夠不夠明顯：有螢幕閃光 + 震動 + 文字 banner，畫面很亂的時候還是看得出「有事發生」嗎 | `restock_flash_strength=0.34`、`restock_shake_strength=5.0` | |
| 4.11 | 補貨區視覺（外圈+柔光）在敵人堆裡會不會被蓋住看不到——這輪視覺半徑刻意比實際判定範圍大 25%（`restock_visual_scale=1.25`），只是畫面變大，判定範圍沒變 | | |

## 五、清除障礙事件測試（新增）

目的：收集數值調參的第一手資料，跟補貨事件是同一個目的，但這是不同形狀的任務
（多點、主動攻擊，不是單點站樁）。按 H 多測幾次。

**觸發方式**：確認第一步「測試前準備」已把 `hazard_debug_key_enabled` 打開，遊戲中按 **H**。
只要事件目前沒在進行中，可以連續按好幾次重複測試。**注意**：如果補貨事件還在進行中按 H
應該完全沒反應，這是刻意的排程保護，不是 bug（見第六節）。

| # | 測項 | 目前預設值 | 正常 / 有問題 / 備註 |
|---|---|---|---|
| 5.1 | hazard 出現的位置（場地中央外圍環狀區域）跑過去會不會覺得太遠或太密集 | 距中心 160–380px，2-3 個 | |
| 5.2 | 每個 hazard 要打 3 下才清除，感覺是「剛好有存在感」還是「太拖、打到膩」 | `hazard_hits_required=3` | |
| 5.3 | 2-3 個 hazard 同時存在，玩家會不會自然分頭處理，還是都擠去打同一個 | `hazard_count_min/max=2/3` | |
| 5.4 | hazard 存在期間持續生成滑地，壓力感受如何——是「不管它會越來越麻煩」還是感覺不出差異 | `hazard_grease_interval=2.5` | |
| 5.5 | 清除障礙的成功回饋（客訴 -1、暫停生成、音效）夠不夠讓人覺得「解決了一個問題」 | `hazard_success_relief=1`、`hazard_success_pause=1.5` | |
| 5.6 | 清除障礙的失敗回饋（多生成 3 隻敵人）夠不夠有懲罰感 | `hazard_fail_spawn_count=3` | |
| 5.7 | hazard 的警示三角視覺（含底部進度條）在混亂畫面裡看不看得清楚哪個快清完了 | | |
| 5.8 | 整體感受：清除障礙像不像「第二個任務」而不是「補貨事件的翻版」或「突然亂入的東西」 | 主觀判斷，這是這輪最想知道的 | |

## 六、事件節奏總控測試（新增，這輪的重點）

目的：確認補貨事件跟清除障礙事件不會互相搶戲、擠壓最後衝刺。**這節建議正常遊玩測，
搭配偶爾用 debug 鍵製造邊界情況**。

| # | 測項 | 正常 / 有問題 / 備註 |
|---|---|---|
| 6.1 | **hazard 是否太靠近 sprint**：正常遊玩一輪，清除障礙事件結束的時間點，離 90 秒最後衝刺還有沒有喘息空間，還是感覺兩件事黏在一起 | |
| 6.2 | **補貨和 hazard 是否連太緊**：補貨事件一結束，清除障礙的開始 banner 是不是幾乎立刻跳出來，感覺像連續轟炸而不是「先喘口氣、再來一波」 | |
| 6.3 | **hazard 數量/血量是否太拖**：如果清除障礙一直沒打完，會不會導致它被排程保護硬性收緊 timeout（甚至逼近 4 秒下限），變成一個明顯來不及做完的事件 | |
| 6.4 | 用 R/F9 故意讓補貨事件拖到快超時才過（或直接失敗），觀察清除障礙是不是確實延後到補貨結束 + 8 秒後才出現 | |
| 6.5 | 用 H 在補貨事件進行中按下去，確認畫面上真的沒有任何反應（排程保護生效） | |
| 6.6 | 把 `Hazard Skip If Too Late` 關掉（改成 false），刻意讓遊戲拖到很晚才觸發清除障礙，確認事件還是會出現、但時限被明顯壓縮，而不是直接跑進最後衝刺裡 | |
| 6.7 | 兩個事件的 toast 文字（開始/成功/失敗）有沒有任何一次同時出現在畫面上、疊字看不清楚 | |

| `hazard_min_delay_after_restock` | 8.0 | main.gd `@export_group("Hazard Event Scheduling")` | |
| `hazard_min_time_before_sprint` | 12.0 | 同上 | |
| `hazard_skip_if_too_late` | true | 同上 | |

`restock_trigger_elapsed` 跟 `early_grace_duration` 目前刻意設成同一個值（都是 45），
如果你決定調其中一個，記得也考慮要不要跟著調另一個，理由見 [docs/level_event_plan.md](level_event_plan.md) 的「跟補貨事件的關係」那段。

`hazard_trigger_elapsed` 不是保證觸發時間，實際觸發時機還要看補貨事件何時結束、離

如果還有其他測試過程中覺得該調的數值（例如雞排攤的某個武器數值、補貨成功的客訴減免量），

## 八、結算畫面測試（新增）

目的：確認勝利/失敗畫面顯示的 8 項統計數字，是不是真的對應到這局實際發生的事，不是顯示假的或算錯的數字。**這節建議搭配 debug 鍵刻意製造各種組合**（例如故意觸發補貨失敗+清除障礙成功，或刻意不觸發任何事件），才測得到完整的顯示邏輯，不是只測一種結局。

### 快速測排版：G 鍵

如果只是想看「面板排版撐不撐得住」，不需要真的打出每一種統計組合——`Stats Preview Debug
Key Enabled` 打開後按 **G**，會立刻塞一組隨機假數字進統計、隨機決定補貨/清除障礙的顯示
文字，然後結束這局（交替顯示勝利/失敗面板，兩種都測得到）。連續按 G 幾次，可以很快看過
各種數字長度、各種事件狀態組合下的排版，不用真的把每個事件都手動玩一輪。**這個純粹是排版
工具，數字是假的，看完排版之後真正要驗證數字對不對，還是要照下面的表格實際玩。**

### 統計對應表：哪個數字該在什麼時候增加

| 統計 | 顯示文字 | 什麼情況下會 +1（或更多） |
|---|---|---|
| `friendly_fire_hits` | 友火：X 次 | 任一玩家的子彈**直接命中**另一位玩家（不是連鎖，是子彈打中） |
| `chain_enemy_hits` | 連鎖撞飛敵人：X 次 | 玩家被擊退、高速狀態下撞到敵人（一次連鎖撞到幾隻敵人就 +幾次） |
| `chain_player_hits` | 連鎖撞飛隊友：X 次 | 玩家被擊退、高速狀態下撞到另一位玩家（同上，可能一次 +2 如果雙向都觸發） |
| `big_enemy_breaks` | 大型破甲：X 次 | 大型饕客被雙人在 2.5 秒內合力打破防（不是普通命中，是真的破防那一下） |
| 補貨/清除障礙結果 | 補貨：X／障礙清除：X | 見第四、五節，觸發後看事件本身怎麼結束 |

## 九、讀圖性配色測試（新增）

目的：確認上一輪「讀圖性配色重分配 v1」（見 [readability_palette.md](readability_palette.md)）
真的解決了問題，不是紙上談兵。**這節看的不是好不好看，是看不看得懂**——同樣的畫面，你要
問自己「這是誰」「這是任務還是危險」，答案應不應該幾乎不用想。

### 測試方式

1. 預設 P1（熱狗）+ P2（珍奶）跑一輪，走完整局節奏（或用 debug 鍵加速）
2. 把 `P2 Character Override` 指到 `chicken_cutlet.tres`，用 P1（熱狗）+ P3（雞排）再跑
   一輪——這是專門測 `PLAYER_HEAVY` 跟 `PLAYER_RISK` 撞不撞色/撞不撞形狀的組合
3. 用 debug 鍵依序觸發：R/F9（補貨事件）、H（清除障礙事件）、正常等到最後 30 秒（sprint
   警告）、G（結算畫面）——每個事件觸發時都停下來看一眼，不要只是按過去

### 測項

## 十、測完之後

這份 checklist 的每一項如果都落在「正常」，代表目前這輪（角色資料化 → 音效優先級 →
補貨事件 → 清除障礙事件 → 節奏總控 → 結算畫面 → 讀圖性配色 → 驗證工具）疊起來的系統
是穩的，第一關骨架（warmup → 補貨 → 清除障礙 → 最後衝刺 → 結算）站得住，畫面也有了
基本的讀圖語言，可以放心往下一步走——第一張 playable mockup，或是低成本正式感視覺替換。

如果讀圖性測試（第九節）還是有撞色/看不懂的地方，先回頭調 `gameplay_palette.gd` 裡的
數值，不用急著進美術，色票本身沒調對，畫上去的正式素材一樣會撞。

如果有「有問題」的項目，先處理完再繼續往上疊功能——這是這一步驗證存在的意義：
不要在地基還沒踩實的狀態下繼續蓋樓。
