# Art Readability Brief v1

建立時間：2026-07-17
用途：玩法骨架（warmup → 補貨 → 清除障礙 → 最後衝刺 → 結算）已經站得住了，現在畫面上
除了三個角色的顏色差異之外，幾乎全部是圓圈、三角形、文字 placeholder。這份文件是往
「playable mockup」邁進之前的準備——先把「玩家看不看得懂」想清楚，再決定怎麼畫。

**這份文件不改 gameplay 程式碼，也不匯入正式素材。** 內容是根據目前 `_draw()` 系統的
實際顏色/形狀盤點寫出來的（不是憑印象），盤點方法見文末附錄。

---

## 一、視角與讀圖原則

- **固定 top-down 2D，1280×720，不縮放不平移**——整個場地隨時全部可見，沒有攝影機幫你
  引導視線，畫面上發生的所有事都要靠美術語言自己被看見
- **分層優先序**（誰該在視覺上「最搶眼」到「最不搶眼」）：玩家角色 > 友火 projectile >
  任務物件（補貨區/hazard）> 敵人（含大型）> 地面效果（滑地/壓力區）> 背景。目前程式碼
  沒有刻意做分層（繪製順序基本等於節點生成順序），這是美術跟工程都要留意的地方
- **讀圖性的測試時機不是安靜畫面，是最亂的那一刻**——這款遊戲的爽點就是失控潮/衝刺時
  畫面塞滿敵人+友火+特效，美術評估「看不看得懂」一定要在這種畫面下測，不能只看單一角色
  站在空地上的效果圖
- **顏色要對應「意義」，不是只對應「好看」**——這是這份文件盤點後發現的最大問題，見下一節

### 現況最大的讀圖風險：色彩系統目前是「意外重複」，不是「刻意分工」

實際比對目前所有 `_draw()`/`@export var *_color` 的數值後，發現至少三組視覺上幾乎分不出來
的暖橙色，被用在完全不相關的系統上：

| 色群 | 數值範圍（R,G,B） | 目前被誰用 |
|---|---|---|
| 群組 A（深橙） | ≈(1.0, 0.48–0.55, 0.05–0.10) | P1 熱狗攤身體色、stage2 危險 banner/場地染色、衝刺計時器閃爍色、美食廣場 stage2 外圈光暈 |
| 群組 B（亮金） | ≈(1.0, 0.75–0.82, 0.05–0.35) | P1 熱狗攤子彈色、補貨區主色+開始閃光、hazard 警示物件主色、衝刺計時器主色 |
| 群組 C（琥珀） | ≈(0.82–1.0, 0.55–0.78, 0.12–0.22) | 大型饕客的 P1 破防條顏色、大型饕客外框色、雞排攤身體色/子彈色 |

換句話說：**「這是我的角色」「這是危險警告」「這是我該去的任務點」「這是計時器」目前用的
是幾乎同一個顏色**，只靠飽和度/亮度的微小差異區分（多數 channel 差距在 0.02–0.05 之間，
肉眼在靜態畫面都不一定分得出來，更不用說混亂畫面）。相對地，冷色只有珍奶攤（藍）跟 P2
的破防條（青）在用，紫/綠只出現在突變卡片上——**冷色系統目前完全沒被拿來做「安全/中性/
任務」這種語意分工，暖色系統則是被四五個不相關的系統瓜分**。

這不是「配色不夠好看」的問題，是「同一顏色現在承擔了太多不同意義」的結構性問題，美術
規劃時建議優先解決。

> **✅ v1 已套用**（2026-07-17）：上面三組撞色已經拆開，色票本體跟每個決定的理由記錄在
> [readability_palette.md](readability_palette.md)。這輪只調整 placeholder 顏色/少數
> marker 形狀，沒有匯入正式素材，也沒有動玩法數值——真正的美術素材進來後，建議延續同一套
> 「一個 gameplay role 一種主色相」的分工原則，不用照抄這裡的精確數值。

## 三、角色 Silhouette 需求

三個角色目前的差異幾乎全部靠數值（見 [character_roster.md](character_roster.md)），
視覺上只有顏色 + 兩種 marker 形狀（圓/方）可用，三個角色卻要對應三種完全不同的「風險
定位」，形狀語言明顯不夠用。建議用定位而不是夜市身份去想 silhouette：

| 定位 | 現在的角色 | Silhouette 方向建議 |
|---|---|---|
| **slow-heavy**（慢、重、範圍大） | 熱狗攤 | 輪廓應該是全場最「厚重」的——寬、矮、佔地大，武器/道具視覺上應該明顯比另外兩個角色的投射物大一號，移動時最好有明顯的「笨重感」動畫語言（大幅度搖晃、慢啟動慢煞車） |
| **fast-burst**（快、密、單發弱） | 珍奶攤 | 輪廓應該是全場最「細窄」的——瘦、高、佔地小，強調移動的靈活感（小幅度快速抖動、殘影），武器應該明顯是「一串小東西」而不是「一個大東西」 |
| **heavy-risk**（慢中帶重、最高擊退、最容易誤傷） | 雞排攤 | 這個定位目前跟 slow-heavy 最容易撞：建議不要只是「熱狗的加重版」，輪廓應該傳達「不穩定/危險」而不是單純「更大更慢」——可以考慮不對稱輪廓、警示色的局部點綴（例如武器本身帶危險視覺語言），跟熱狗攤的「厚重但穩定」做出性格上的區隔，不是只有數值上的區隔 |

**核心要求**：三個角色即使變成純黑剪影（去掉顏色、去掉貼圖細節），光看外形輪廓也要能
分出「這是哪一個」。原本圓形+方形兩種 marker 撐不住第三個角色（[character_roster.md](character_roster.md)
已經記錄過這個問題），[readability_palette.md](readability_palette.md) 這輪加了第三種
`marker_shape`（三角形）給雞排攤用，暫時解決「兩種形狀撐三個角色」的問題——但這只是
placeholder 等級的最小修正，不是這裡要求的正式 silhouette 設計。真正的角色美術還是要照
上面表格的定位（slow-heavy / fast-burst / heavy-risk）做出真正的外形差異，不能滿足於
「反正三種 marker 形狀都不一樣」就結束。

## 四、主題中立版本與夜市版本對照

延續 [theme_dependency_audit.md](theme_dependency_audit.md) 的結論——命名已經確認主題
中立，這裡把**視覺**也做同一層對照，確保美術資產命名/設計時不會不小心把夜市畫死：

| 抽象角色 | 夜市版本 | 中性/其他主題版本範例 |
|---|---|---|
| 任務標記物（補貨區） | 補貨箱、攤位貨架 | 補給站、修理面板、魔法儀式圈、能量核心 |
| 可破壞警示物（hazard） | 油污桶、雜物堆 | 故障機器、魔法污染源、失控道具、外洩管線 |
| 地面持續型危害（grease/滑地） | 地板油漬 | 冰面、黏液、電流地板、油壓洩漏 |
| 中央防守目標（美食廣場） | 美食廣場攤位群 | 控制核心、傳送門、發電機、聖壇 |
| 一般敵人 | 饕客（顧客） | 喪屍、機器人、入侵怪物、失控訪客 |
| 大型敵人 | 大胃王饕客 | 精英怪、巨型機器人、頭目使魔 |
| 壓力計數器（客訴） | 客訴數 | 警報等級、感染值、故障率、混亂值 |

美術資產的**檔名/圖層命名**建議直接用左欄的抽象角色（`task_marker`、`hazard_object`、
`slip_zone`、`center_target`⋯），不要用「補貨箱.png」這種綁死夜市的檔名——這樣換主題時
只要換貼圖內容，不用連檔名/程式碼一起改，跟 [theme_dependency_audit.md](theme_dependency_audit.md)
裡「最小成本換皮」的結論一致。

## 五、第一批 Mockup 需求

一張 **1280×720**、實際遊戲視角（不是宣傳圖，不是 hero art，不做商店頁美術）的靜態畫面，
內容必須包含：

- 2 位玩家（不同角色，展示 silhouette 差異）
- 3-5 隻一般敵人（模擬正常波次密度）
- 1 隻大型敵人（含破防條 UI）
- 1 個補貨區（進行中狀態，含進度環）
- 1-2 個 hazard（不同受擊進度，展示「還剩多少要打」）
- 1-2 灘 grease/滑地
- 中央防守目標（美食廣場，任一 stage 狀態皆可）
- 現有 UI：客訴數、計時器、角色名稱 debug 文字
- 場面要「混亂但看得懂」——這張圖存在的目的就是驗證第一節「讀圖原則」，如果畫完這張圖
  自己都分不出誰是誰，代表色彩/形狀系統要重新設計，不是這張圖畫得不夠好看

不需要：載入畫面、主選單美術、結算畫面美術、任何行銷用途的關鍵視覺（key art）。

## 六、附錄：盤點方法

這份文件的「現況」部分不是憑印象寫的，是實際讀取以下檔案的 `_draw()` 函式與
`@export var *_color` 欄位取得的精確數值後比對出來的：`player.gd`、`player_character.gd`
+ `resources/characters/*.tres`、`enemy.gd`、`big_enemy.gd`、`projectile.gd`、
`grease_puddle.gd`、`restock_event.gd`、`hazard_object.gd`、`food_court.gd`、
`hit_effect.gd`、`main.gd`（危險暈影/banner/計時器相關顏色）。逐一數值比對詳見這輪
對話紀錄，這裡只收錄結論。
